# CodeBinder Java redistributable components

The static support classes (Java package `CodeBinder`) that the Java code
generated by `CodeBinder.Java` compiles against. They used to be emitted into
every generated project; they are now published as maven artifacts instead, so
that several generated libraries can coexist on one classpath.

## Artifacts

| Artifact | Target | Bytecode | Finalization |
|---|---|---|---|
| `org.codebinder:codebinder-redist` | JDK projects | 52 baseline + 53 overlay | `Object.finalize()` on JDK8, `java.lang.ref.Cleaner` on JDK9+ |
| `org.codebinder:codebinder-android-redist` | Android projects | 55 | `java.lang.ref.Cleaner`, requires **API level 33** |

`codebinder-redist` is a [multi-release jar](https://openjdk.org/jeps/238): the
baseline classes target JDK8 and know nothing about `java.lang.ref.Cleaner`,
while `META-INF/versions/9/CodeBinder/BinderUtils.class` uses it directly. The
JVM picks the right one, with no reflection on either side.

Android gets a separate artifact rather than the multi-release one because the
Android toolchain doesn't handle `META-INF/versions` consistently.

**The two artifacts carry the same `CodeBinder` package and must never be on the
same classpath.**

## Consuming

Maven, for a generated JDK wrapper:

```xml
<dependency>
    <groupId>org.codebinder</groupId>
    <artifactId>codebinder-redist</artifactId>
    <version>1.0.0</version>
</dependency>
```

Gradle, for a generated Android library. It has to be `api`, not
`implementation`: the generated public signatures expose `CodeBinder.HandleRef`,
`CodeBinder.IntegerBox` and friends, so the package must reach the consumers of
the AAR.

```groovy
api 'org.codebinder:codebinder-android-redist:1.0.0'
```

## Layout

```
src/main/java/CodeBinder/                 35 classes shared by both artifacts
src/main/java8/CodeBinder/BinderUtils.java     baseline, no Cleaner, no reflection
src/main/java9/CodeBinder/BinderUtils.java     java.lang.ref.Cleaner
src/main/resources-android/               proguard rules, android artifact only
jdk/pom.xml, android/pom.xml              the two artifacts
```

The two `BinderUtils` variants must keep identical member signatures apart from
the private `_cleaner` field, since javac may resolve a consumer against either
one depending on its `--release`. Check with:

```
javap -p CodeBinder/BinderUtils.class
javap -p META-INF/versions/9/CodeBinder/BinderUtils.class
```

## Building

Requires a JDK 11 or newer toolchain (the `release 9` and `release 11` compiler
settings).

```
./do-pack-java-redist.ps1            # build both jars
./do-pack-java-redist.ps1 Upload     # publish
```

`Upload` publishes each artifact with `deploy:deploy-file`, to a repository
that can be personalized with the following variales.

```powershell
$env:CODEBINDER_JDK_MAVEN_REPO = "https://<repoid>@<host>/<path>"
$env:CODEBINDER_ANDROID_MAVEN_REPO = "https://<repoid>@<host>/<path>"
```


Either variable left unset falls back to maven central with the id `central`.
A value without the `<repositoryId>@` part is rejected outright.

What consumers resolve is a parent-free descriptor with the version resolved,
written by `flatten-maven-plugin` to `<module>/target/pom-publish.xml`. The
aggregator pom is never published.
